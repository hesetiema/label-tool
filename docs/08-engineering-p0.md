## 1. 撤销重做：命令模式（Command Pattern）

### 面试官问："编辑器类工具怎么实现 undo/redo？"

这是设计模式的经典应用题。标准答案：**把每次操作封装成命令对象，用两个栈记录历史**。

```ts
// 命令对象自带操作前后状态
interface HistoryCommand<T> {
  label: string      // "移动框" —— 用于 UI 显示
  before: T          // 操作前状态
  after: T           // 操作后状态
}
// undo() → 弹出栈顶，恢复 before
// redo() → 从重做栈弹出，恢复 after
```

### 两种实现路线的取舍

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **差量命令** | 每个操作写自己的逆操作（移动 +dx → 撤销 -dx） | 省内存 | 每种字段都要写逆逻辑，容易漏，嵌套操作难处理 |
| **状态快照**（本项目） | 操作前后各存一份完整状态，undo 就是切回 before | 逻辑极简，绝不会漏，正确性有保证 | 内存占用大 |

标注工具的状态只是一堆小框（几十到几千个 × 5 个数字），快照非常便宜——所以本项目选快照，但用命令对象的接口包起来。面试时这样讲：**"我评估了状态规模，选择了快照方案，并用命令模式统一接口"**——体现的是取舍判断，而不是背模式。

### 三个容易漏的细节（都是加分点）

1. **新操作必须清空重做栈**。否则 undo 之后再做一个新操作，redo 会跳到旧的分支上——这是"分支历史"问题。
   ```ts
   commit(before, after) {
     this.undoStack.push(...)
     this.redoStack = []   // ← 关键
   }
   ```

2. **连续操作要合并**。拖动 yaw 滑杆触发几十次 input 事件，如果每次都记一条历史，用户要按几十次 Ctrl+Z 才能退回。本项目用 `mergeKey` + 时间窗口（700ms）合并：
   ```ts
   if (mergeKey === top.mergeKey && now - top.timestamp < 700) {
     top.after = after    // 只更新 after，不新增条目
     return
   }
   ```

3. **快照必须深拷贝**。如果 before 和 after 指向同一个对象，修改后 before 也跟着变，undo 就失效了。
   本项目用 `JSON.parse(JSON.stringify(x))`——这里还有个真实踩坑：`structuredClone` 在部分旧版 WebView / headless 浏览器不可用，会导致整个初始化中断。面试讲这个细节，说明你真的在浏览器里跑过。

### 对应源码
- `core/history.ts`：HistoryStack 类 + cloneBoxes
- `App.vue`：所有编辑操作都经过 `mutate(label, fn, mergeKey)` 统一入口——**关键设计**：不这么做就会出现"有些操作能撤销、有些不能"。

## 2. 多帧时序：obj_id 跨帧一致 + 轨迹插值

### 为什么自动驾驶标注必须有时序？

单帧标注只回答"这一帧有什么"；时序标注要回答"**同一目标在连续帧里在哪**"。感知模型的跟踪/预测模块需要跨帧一致的 obj_id 才能训练。这也是所有 JD 都提到"多帧时序一致标注"的原因。

### 三个核心算法

**① 最近邻数据关联**（`associateNearest`）—— 教学版

给新帧里没有 id 的框匹配上一帧的目标：计算所有框对的中心距离，从小到大贪心配对（每个目标只用一次），超过阈值（默认 6m）就不关联——可能是新出现的目标。

**② 全局最优关联**（`core/tracker.ts`）—— 生产级版本，后续补上

贪心最近邻的致命问题：**局部最优不等于全局最优**，而且光看距离会掉进陷阱。
经典反例（工具里点「贪心 vs Hungarian 关联演示」可现场看）：

```
上一帧:  A 在 x=8     B 在 x=12
当前帧:  A'在 x=12    B'在 x=8     ← 两车相向交叉换位
```

- **纯距离贪心**：A 离 B' 距离 0、B 离 A' 距离 0 → 总距离 0，看似"完美匹配"，
  但两个 ID 完全串了。更讽刺的是，**贪心的分数越是完美，错得越离谱**。
- **Kalman + Hungarian**：Kalman 用速度预测 A 应该在 12、B 应该在 8，
  于是 A→A'、B→B'，总距离同样是 0，但 ID 正确保持。

实现包含三块：
- `hungarian()`：Kuhn-Munkres 算法求最小权二分图匹配，O(n³) 而非暴力 O(n!)。
  **工程坑**：代价矩阵收益必须加基础值（+1），否则当代价全为 0 时收益全 0，
  Hungarian 分不清"真实配对"和虚拟节点，返回空结果。
- `KalmanFilter2D`：常速度模型，状态 [x, y, vx, vy]，预测→门控→观测更新。
  观测噪声下 10 步收敛到速度真值（实测 vx=2.11 vs 真值 2.0）。
- `associateHungarianKalman()`：完整链路 = Kalman 预测位置 → 距离门控拒绝不合理配对
  → Hungarian 全局分配 → 观测修正 Kalman 状态。

> 面试讲法：先讲贪心的反例（白板画两车交叉），再说"所以我补了生产级版本：
> Kalman 预测 + 门控 + Hungarian 全局匹配"。这比单纯说"我知道 Hungarian"有力得多。

**③ 角度插值走最短弧**（`lerpAngle`）—— 新手必踩的坑

yaw 从 +3.1 直接线性插值到 -3.1，中点会算出 0（绕了一大圈 6.2 弧度），而实际只转了 0.08 弧度。正确做法先把角度差规范到 [-π, π]：

```ts
let d = b - a
while (d > Math.PI) d -= 2 * Math.PI
while (d < -Math.PI) d += 2 * Math.PI
return a + d * t
```

**④ 轨迹插值**（`interpolateTracks`）

标注员只标首末帧，中间帧用线性插值自动补全：对每个 obj_id，找到它出现的所有帧，在相邻两次观测之间补全缺失帧的 position / scale / yaw。本项目 5 帧演示序列里，3 条只标了首末帧的轨迹会自动补出 9 个框。

### 对应源码
- `core/sequence.ts`：FrameData、lerpAngle/lerpBox、associateNearest、interpolateTracks、generateDemoSequence
- `App.vue`：时间轴切帧时**先把当前帧编辑结果写回序列**（否则切走再切回会丢修改）

## 3. 大规模点云性能：从 100 万点到 27 万点

### 面试官问："一帧十几万个点，浏览器怎么不卡？"

真实 LiDAR 一帧 10~20 万点，一段序列百万级。三个层次的优化：

**① 数据结构层**——用 `Float32Array` 而不是普通 JS 数组。
普通数组存的是指针 + double，内存和 GC 压力大；Float32Array 是连续二进制块，正好是 WebGL 顶点缓冲需要的格式，可以直接交给 GPU，零转换。

**② 算法层**——体素下采样 + 距离 LOD（本项目实现）

- **体素网格下采样**：把空间切成小立方体（如 0.5m），每格只保留一个代表点（格内坐标平均）。点数从 O(N) 降到 O(非空容量数)，且均匀保形。这是 PCL 里最常用的滤波器。
- **距离 LOD**：离传感器近的点全保留（细节重要），远处的按比例抽稀。符合人眼感知——远处的点本来就挤在一起，抽掉一半看不出来。

**③ 渲染层**——BufferGeometry 一次上传，避免每次编辑都重建。

本项目 `syncViewer()` 里用 `lastCloudRef` 比较引用：只有点云真的换了才重新 `setPointCloud`，编辑框时只更新框的几何体。这是很容易被忽略但收益极大的优化。

### 实测数据（本项目 `pnpm test:core` 验证过算法，`?data=perf` 页面实测帧率）

| 阶段 | 点数 | 耗时 | 内存 |
|---|---|---|---|
| 原始生成 | 1,000,000 | 120ms | 11.4 MB |
| 体素下采样 (0.5m) | 500,995 (−49.9%) | 1,355ms | — |
| 距离 LOD (近 45m 全留 / 远留 50%) | 270,889 (−45.9%) | 36ms | 3.1 MB |
| **总压缩** | **3.7×** | — | **−73%** |

> 面试话术：不要只说"我做了下采样"，要说出**参数、压缩比、耗时、内存变化**。数字是工程能力最直接的证据。

## 4. 这三个能力在面试里怎么讲

| 追问 | 你的回答要点 |
|---|---|
| undo 怎么实现？ | 命令模式 + 双栈；评估状态规模后选快照而非差量；提到分支清空、合并、深拷贝三个坑 |
| 连续帧 ID 怎么保持一致？ | 教学版最近邻；生产级用 Kalman 预测+门控+Hungarian（已实现，见第 2 节交叉案例）；角度插值走最短弧；首末帧插值补全 |
| 一百万点怎么不卡？ | Float32Array 零拷贝 → 体素+LOD 减点 → BufferGeometry 复用；报出实测压缩比与耗时 |
| 有没有踩过什么坑？ | `structuredClone` 兼容性导致初始化中断；Hungarian 收益全 0 时分不清虚拟节点（真实踩坑，见第 2 节） |

**诚实边界**：这是学习实现——撤销是全局快照（生产会按文档维护 + 协同 OT），关联算法已实现 Kalman+Hungarian 但只用 2D 常速度 + 欧氏距离（生产用马氏距离 + JPDA/多假设跟踪处理遮挡），插值只用线性（生产用轨迹优化）。主动说出边界，比被追问出来强得多。
